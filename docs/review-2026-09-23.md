### P0-1　第二课堂 token 账号键口径不一致 —— 二课卡片永久显示「未绑定」，积分缓存永不写入

**位置**
- `secondclass/SecondClassroomStore.kt:54`（读，原实现不做归一化）
- `widgetboard/CardWidgetDataLoader.kt:63,73`（读，传 `currentAccountStorageKey`）
- `ui/route/WidgetBoardRoute.kt:54,113`（读，传 `currentAccountStorageKey`）
- 写入侧统一传 `currentAccountKey`：`ui/screen/SecondClassLoginDialog.kt:66,104`、`ui/route/SecondClassroomRoute.kt:60`、`ui/route/SecondClassActivityCenterRoute.kt:74`

**触发条件**：任意已绑定第二课堂的账号，打开「组件工作台」查看第二课堂卡片，或把「第二课堂积分」卡片添加到桌面。**100% 复现**。

**根本原因**

本工程并存两种账号键，且**二者不可能相等**：

```java
// manager/UserManager.java:446
return school.id + "::" + identity.trim();        // → hnnu::2024001

// manager/UserManager.java:603
return key.replaceAll("[^A-Za-z0-9_.-]", "_");    // → hnnu__2024001
```

二课各页面传 `currentAccountKey`（含 `::`），而新加的桌面组件传 `currentAccountStorageKey`（`::` 已被替换成 `__`）。`SecondClassroomStore` 直接拼原始键、不做归一化，于是**写进 `token_hnnu::2024001`、读 `token_hnnu__2024001`**，读出来恒为空串。

值得注意的是，本项目其余按账号落盘的存储**都做了归一化**（`CourseCacheManager.normalizeAccountKey`、`GradesCacheManager`、`SecondClassOverviewCache.normalize`），`SecondClassroomStore` 是唯一的例外；`ui/route/SettingsRoute.kt:270-273` 甚至已经用注释记录过同类踩坑（"这里若用 currentAccountKey……红点永远是 0"），说明这是项目已知的一类陷阱，只是本模块漏掉了。

**影响范围**（两级放大）

1. `bound` 恒为 `false` → `widgetboard/CardWidgetRenderer.kt:158` 与 `ui/screen/WidgetBoardCards.kt:649` 恒走「还没绑定第二课堂 / 二课未绑定」分支，用户明明绑定过也显示未绑定。
2. `WidgetBoardRoute.kt:115-118` 因 token 为空提前 `return@LaunchedEffect`，导致 `SecondClassOverviewCache.save`（`:124`，全仓库唯一写入点）**永不执行** —— 即使修好 `bound`，模块列表也永远是空的。

**修复**：在存储层做键归一化（与其它缓存同一条规则），并对老数据做一次性迁移，避免用户重新登录。

**修改后代码**（`secondclass/SecondClassroomStore.kt`）

```kotlin
    /**
     * 账号键归一化：与 `UserManager.toStorageKey`、`SecondClassOverviewCache.normalize`
     * 用同一条规则（非 `[A-Za-z0-9_.-]` 一律换成 `_`）。
     */
    internal fun normalize(accountKey: String): String =
        accountKey.ifBlank { "default" }.replace(Regex("[^A-Za-z0-9_.-]"), "_")

    private fun tokenKey(accountKey: String) = KEY_TOKEN_PREFIX + normalize(accountKey)

    /**
     * 与 [accountKey] 指向同一个账号、但**写法不同**的历史键（如 `token_hnnu::2024001`）。
     *
     * 为什么不能直接拼 `token_ + accountKey` 来还原旧键：调用方可能传的是已归一化的
     * storage key，从它反推不出旧键的字面量。所以统一按"归一化后是否指向同一账号"来认，
     * 这样无论调用方传哪种口径都能认出老数据。
     */
    private fun staleTokenKeys(p: SharedPreferences, accountKey: String): List<String> {
        val normalized = normalize(accountKey)
        val current = KEY_TOKEN_PREFIX + normalized
        return p.all.keys.filter { candidate ->
            candidate.startsWith(KEY_TOKEN_PREFIX) && candidate != current &&
                normalize(candidate.removePrefix(KEY_TOKEN_PREFIX)) == normalized
        }
    }

    fun token(context: Context, accountKey: String): String = readToken(prefs(context), accountKey)
    fun saveToken(context: Context, accountKey: String, token: String) = writeToken(prefs(context), accountKey, token)
    fun clearToken(context: Context, accountKey: String) = removeToken(prefs(context), accountKey)

    // ---- 以下三个是纯存储原语，直接吃 SharedPreferences ----
    // 不经过 Context 是为了让 JVM 单测能喂内存实现（同 ScheduleCacheStore 的做法）：
    // 键口径的一致性完全由这几个函数决定，必须有回归测试盯着。

    internal fun readToken(p: SharedPreferences, accountKey: String): String {
        if (accountKey.isBlank()) return ""
        val key = tokenKey(accountKey)
        p.getString(key, "").orEmpty().takeIf { it.isNotBlank() }?.let { return it }
        // 迁移：老版本把 token 写在未归一化的键上，读到就搬到归一化键（只搬一次）。
        val stale = staleTokenKeys(p, accountKey).firstOrNull() ?: return ""
        val migrated = p.getString(stale, "").orEmpty()
        if (migrated.isNotBlank()) p.edit().putString(key, migrated).remove(stale).apply()
        return migrated
    }

    internal fun writeToken(p: SharedPreferences, accountKey: String, token: String) {
        if (accountKey.isBlank()) return
        val editor = p.edit().putString(tokenKey(accountKey), token)
        // 顺手清掉历史写法，避免同一账号留两份、日后被迁移逻辑"复活"成旧值。
        // staleTokenKeys 已排除当前键本身，所以不会把刚写进去的 token 删掉。
        staleTokenKeys(p, accountKey).forEach { editor.remove(it) }
        editor.apply()
    }

    internal fun removeToken(p: SharedPreferences, accountKey: String) {
        if (accountKey.isBlank()) return
        val editor = p.edit()
        staleTokenKeys(p, accountKey).forEach { editor.remove(it) }
        // 显式再删一次目标键：staleTokenKeys 不包含它，且这样在"目标键不存在"时也幂等
        editor.remove(tokenKey(accountKey)).apply()
    }
```

> **实现过程中的一次真实纠错**：第一版迁移逻辑是「拼出 `token_ + 原始 accountKey` 再读」。新增的回归测试立刻暴露了它的缺陷 —— 当调用方传的是**已归一化**的 storage key（桌面组件正是如此）时，无法反推旧键字面量，迁移会静默失效，老用户升级后 token 直接丢失、必须重新绑定。最终实现改为「扫描所有 `token_` 前缀的键，按归一化结果匹配」。这正是把关键不变量写成测试的价值。
>
> 未一并归一化 `credentialKey`（密码）是**刻意的**：`CredentialStore` 的键是 `sha256(accountKey)`，改了会让所有已保存密码失效。当前所有密码调用点都统一传 `currentAccountKey`，不存在口径分歧。

### P0-2　考前提醒在开机 / 应用更新 / 改时间后静默失效

**位置**：`schedule/ExamReminderScheduler.kt:141-142`（修复前）

**触发条件**：为一门 24 小时后开考的考试设置提醒 → 重启手机（或应用更新、改系统时间、改时区）→ 闹钟不再触发。**必现**。

**根本原因**

`reconcile()` 用「计划表里已存在同一条计划」作为「闹钟已经排好」的判据：

```kotlin
        desired.forEach { (id, plan) ->
            if (existing[id] == plan) return@forEach      // ← 计划没变就跳过 set()
```

但**计划表存在 `SharedPreferences` 里，闹钟活在 `AlarmManager` 里**。开机、应用更新、强制停止、改时间都会让系统清空所有闹钟，而 `SharedPreferences` 原样保留。重排时 `existing[id] == plan` 仍然成立，于是被当作"已排"跳过，`setExactAndAllowWhileIdle` 永不执行。

同项目的 `ScheduleReminderScheduler`（课前提醒）做对了这一点 —— `CourseReminder.kt:99` 用 `PendingIntent.FLAG_NO_CREATE` 真实探测闹钟是否存在：

```kotlin
        if (existing[id] != plan || !alarms.exists(plan.reminder.key)) alarms.schedule(plan)
```

考前提醒是后加的模块，漏掉了这层校验。`ExamReminderReceiver` 在 `BOOT_COMPLETED` 时确实会调用 `reconcile`，但由于上述判据，这次重排是**空操作**。

**影响范围**：`ExamReminderScheduler` 的全部功能 —— 考前提醒在设备重启后彻底不可用，且用户无从察觉（UI 上该考试的提醒开关仍是打开的）。

**修改后代码**

```kotlin

        // 判据必须同时满足"计划表里已有同一条"**且**"闹钟真的还挂在系统里"：
        // 计划表存在 prefs 里，而闹钟活在 AlarmManager 里 —— 开机、应用更新、
        // 强制停止、改时间都会把闹钟清空，计划表却原样留着。只看计划表的话，
        // 重排会把它们全部当成"已排"跳过，考前提醒从此静默消失。
        desired.forEach { (id, plan) ->
            if (existing[id] == plan && alarmExists(context, id)) return@forEach
```

```kotlin
    /**
     * 这条闹钟是否**真的**还挂在系统的 AlarmManager 里。
     *
     * `FLAG_NO_CREATE` 在 PendingIntent 不存在时返回 null，正好是我们要的判据
     * （Intent 的匹配走 filterEquals，不看 extras，所以这里传 id 只为构造同一个 Intent）。
     * 与 `ScheduleReminderScheduler.alarms.exists()` 是同一套做法。
```

### P0-3　会话被外部替换后，抢课队列不释放前台服务与常驻通知（`isRunning` 永久卡死）

**位置**：`service/GrabService.kt:647-653`、`654-655`、`657-663`（修复前行号）

**触发条件**

1. 抢课队列运行中；
2. 会话令牌被本队列之外的路径替换 —— 用户登出、切换账号，或其它模块（成绩页 / `CookieWatchdog`）触发了一次成功的静默续期；
3. 队列收尾。

**根本原因**

收尾块与异常块都以「会话是否仍是当前」作为执行前提：

```kotlin
                handler.post {
                    if (!currentUser.sessionState.isCurrent(queueSession.get())) return@post   // ← 647
                    isRunning = false
                    ...
                    stopForeground(STOP_FOREGROUND_REMOVE)
                    stopSelf()
                }
            } catch (e: CancellationException) {
                throw e                                                                    // ← 654
```

`queueSession` 只在本队列自己发起续期时被更新（`queueSession.set(result.token)`），无法感知外部替换。链路如下：

1. 令牌被外部替换 → 每个 worker 的 `canContinue`（`GrabService.kt:599`）变为 `false`；
2. `ProtocolGrabRunner.kt:49` 抛 `CancellationException` → `coroutineScope` 抛取消异常；
3. `catch (e: CancellationException) { throw e }` 直接重抛 → **`handler.post` 那段收尾代码根本没机会执行**。

即便不走第 2 步（正常结束），`isCurrent` 守卫也会让收尾被跳过。

**影响范围**

- `isRunning` 永久停在 `true`，`AcademicGrabRuntimeStore.running` 同样停在 `true`；
- `NOTIFICATION_ID` 的 `setOngoing(true)` 常驻通知永不清除，前台服务长期占用；
- `ui/route/AcademicRoutes.kt:419-421` 的 `start()` / `replace()` 因 `running == true` 被拦截，**用户无法再启动任何新任务**；
- 为其它账号启动时被 `bindServiceAccount`（`GrabService.kt:350-357`）拒绝。

**修复**：引入「队列代次」作为队列身份标识，替代用会话令牌判断"这次回调是否属于本次队列"。

**修改后代码**（节选，完整改动见 `git diff`）

```kotlin
     *
     * 只在"代次仍是本次队列"时执行 —— 否则说明用户已经停过它、或新队列已经顶上来，
     * 这时再写状态就是把新队列的界面冲掉。
     */
    private fun finishAcademicQueue(generation: Long, halted: Boolean, failure: String?) {
        handler.post {
            if (!academicQueueRun.isCurrent(generation)) return@post
            isRunning = false
            academicRunners.clear()
            broadcastLog(
                when {
                    failure != null -> "教务任务已暂停：$failure"
                    halted -> "教务队列已停止，请处理提示后重新启动"
                    else -> "教务队列执行结束"
                }
            )
            stopForeground(STOP_FOREGROUND_REMOVE)
            stopSelf()
        }
    }
```

同时 `stopGrabbing()` 也推进代次，确保「用户主动停止」之后不会被迟到的收尾回调重复广播：

### P1-5　并行选课模式下，一次成功的会话续期会让兄弟任务被判死（状态卡在 GRABBING），并可能整队误停

**位置**：`service/GrabService.kt:595-620`（修复前）

**触发条件**

1. 开启「并行模式」（`AcademicRoutes.kt:400`，UI 有开关；正方 `AcademicSystem.ZF.serial == false`，因此 `workers = 2`）；
2. 队列中有 ≥ 2 门课程，两个 worker 同时在跑；
3. 其中一个 worker 触发 `SESSION_EXPIRED` 并**续期成功**。

**根本原因**

每个 worker 在启动时把会话令牌固化到自己的局部变量：

```kotlin
                        semaphore.withPermit {
                            var expected = queueSession.get()          // ← 595 两个 worker 各拿一份旧令牌
                            ...
                            canContinue = { !queueHalted.get() && currentUser.sessionState.isCurrent(expected) }
```

worker A 续期成功后只更新了 `queueSession` 和自己的 `expected`；worker B 的 `expected` 仍是旧令牌 → `canContinue()` 返回 `false` → `ProtocolGrabRunner.kt:49` 抛 `CancellationException`：

- 若 B 已在 `runOnceLocked` 中：B 的协程被取消，**该课程状态永远停在 `GRABBING`**（既不会标 `SUCCESS` 也不会标 `FAILED`，也不再重试）；
- 若 B 先返回 `Paused(SESSION_EXPIRED)`：`GrabService.kt:619-620` 会把 `queueHalted` 置 `true`，而 B 的状态回写在 `:622` 被 `isCurrent` 守卫丢弃 —— **会话明明已续期成功，整队却被判定"需要处理"而停摆**。

更深一层：续期会 `retire()` 旧的 `AcademicSession`（`AcademicSessionStore.kt:98-102`），所有 worker 手里的适配器随之失效。原实现只 `replaceAdapter` 触发续期的那个 worker，兄弟 worker 的适配器仍指向已退休的会话。

**影响范围**：并行模式下的抢课成功率显著下降（部分课程静默不执行），且可能整队误停。

**修改后代码**（最终形态：判据已抽到 `academic/AcademicQueueRun.kt`，`GrabService` 只做委托）

```kotlin
                            // 判据读**共享**的会话令牌（由 AcademicQueueRun 持有），不读各 worker
                            // 自己的局部快照：并行模式下只要有一个 worker 续期成功，整队会话就换新了，
                            // 兄弟 worker 若还拿旧令牌比对，会把自己误判成"会话已失效"而自我取消。
                            runner = ProtocolGrabRunner(
                                adapter,
                                canContinue = { academicQueueRun.canContinue { currentUser.sessionState.isCurrent(it) } },
                            ) {
                                val active = UserManager.getInstance()
                                val pending = academicQueueRun.session()
                                if (!SessionRenewer.canRenew() || pending == null) false
                                else kotlinx.coroutines.suspendCancellableCoroutine { continuation ->
                                    SessionRenewer.request(pending) { result ->
                                        if (continuation.isActive) {
                                            if (result is ...Recovered && active.sessionState.isCurrent(result.token)) {
                                                academicQueueRun.adoptSession(result.token)
                                                // 续期会把旧的 AcademicSession retire 掉，所有 worker 手里的
                                                // 适配器随之失效。必须**整队**换掉：只换触发续期的这一个，
                                                // 兄弟任务下一次请求就会撞上 "Session replaced" 被判死，
                                                // 该课程状态永远停在 GRABBING。
                                                academicRunners.forEach { it.replaceAdapter(AcademicGatewayFactory.create(school, account)) }
                                                continuation.resumeWith(Result.success(true))
                                            } else if (result is ...Superseded) {
                                                continuation.cancel()
                                            } else continuation.resumeWith(Result.success(false))
                                        }
                                    }
                                }
                            }
                            academicRunners += runner
```

事件回写判据同步从「会话是否仍是当前」改为「代次是否仍是本次队列」（原因见 P0-3 的注释：会话续期/登出是运行期的正常事件，拿它做判据会把本次队列的结果整批丢掉）。

> **可测性**：本项的判据与 P0-3 的代次判据一起被抽到 `academic/AcademicQueueRun.kt`（无 Android 依赖），
> 由 `AcademicQueueRunTest` 的 15 项测试覆盖。未做整体 `QueueRunner` 抽离的理由见 §6.3。

### P1-8　「选课成功 / 需要处理 / 登录失效」三类强提醒挂在低优先级渠道上，被系统静默

**位置**（修复后行号）：`service/GrabService.kt:749-771`（`createNotificationChannel` 建两个渠道）、`:727-733`（`postAcademicAttention`，`CHANNEL_ID_ALERT`）、`:1498-1520`（`handleCookieInvalid`，`CHANNEL_ID_ALERT`）、`:2452-2470`（`showSuccessNotification`，`CHANNEL_ID_ALERT`）

**影响范围**：用户会收到一条属于**已删除账号**的考试提醒（含课程名、考试时间、地点），点击后跳到成绩页 —— 而那里已经没有这个账号的数据。属于"用户明确表示不要了、系统却还在提醒"的体验缺陷，且**无法自行消除**（闹钟会一直重排）。

**修改后代码**

```kotlin

        if (!shouldDeliver(plan, user.isLoggedIn, user.isDemoMode, user.currentAccountStorageKey)) return
```

```kotlin
    /**
     * 该计划此刻是否应当播报。
     *
     * 抽成纯函数是为了能被 JVM 单测盯住 —— 它就是"删号 / 登出 / 切号后仍收到考试提醒"
     * 这个缺陷的判据。三条都必须成立：
```

### P2-11　彻底删号未清理「提醒计划」与「学工凭据」—— 四个清理 API 存在但调用点为零

**位置**：`ui/route/SettingsRoute.kt:397-419`（`deleteAccountEntirely`）

**触发条件**：「我的」→ 删除任意账号。

**根本原因**：项目为"按账号落盘的数据"提供了成对的清理 API，但删号路径只接了其中一部分。四个 API **实现完整、语义正确，却一个调用点都没有**（或只被 App 内的解绑按钮调用）：

| 清理 API | 调用点 | 应清理的数据 |
| --- | --- | --- |
| `ScheduleReminderScheduler.clearAccount(account)` | **0** | 课前提醒计划 + 提醒日历 + 闹钟 |
| `ExamReminderScheduler.clearAll(context, accountKey)` | **0** | 考前提醒计划 + 闹钟 |
| `MessageCenterNotifier.reset(context, accountKey)` | **0** | 消息播报基线 + 巡检节流时间 |
| `XuegongStore.clearAccount(context, accountKey)` | 仅 `XuegongScreen` 的「退出学工登录」 | 学工 token + **加密存储的学工密码** |

其中 `ExamReminderScheduler.clearAll` 的注释原文就是"**退出登录 / 删除账号时清掉该账号的提醒**" —— 实现按删号场景写的，却从未被删号调用。

**影响范围**：
1. **学工密码残留**（最值得注意）：`XuegongStore.clearAccount` 会调 `CredentialStore.remove(context, "xg::$accountKey")`。漏掉它，用户执行"彻底删号"后，**学工系统的密码仍以密文留在磁盘上**，与该操作对用户的承诺不符。
2. **提醒闹钟残留**：结合 P1-10，删号后仍可能收到该账号的提醒；即便有了 P1-10 的守卫不再播报，闹钟与计划表条目仍会永久占用（开机还会被重排）。
3. **消息基线残留**：重新添加同一账号时，旧的"已播报"基线会抑制本该播报的未读提醒。

**修改后代码**

```kotlin

            com.hnnujw.course.manager.GradesCacheManager.clearAccount(context, storageKey)

            // 提醒计划同样是按账号落盘的，而且两套提醒都已提供清理 API —— 此前只是没接进来。
            com.hnnujw.course.schedule.ScheduleReminderScheduler.get(context).clearAccount(storageKey)

        com.hnnujw.course.xuegong.XuegongStore.clearAccount(context, record.key)
```

### 4.3　消息中心缓存文件名使用 `hashCode()`，与其它缓存口径不一致（**已修复**）

**原实现**：

```kotlin
    private fun cacheFile(context: Context, accountKey: String): File =
        File(context.cacheDir, "message_center_" + accountKey.hashCode().toString(36) + ".json")
```

项目内其余按账号落盘的缓存统一使用归一化口径（非法字符替换为 `_`），只有这里用 32 位 `String.hashCode()`。两个问题：

1. **两个不同账号若 `hashCode()` 碰撞，会互相读到对方的消息列表**；
2. 文件名是乱码串，排查线上问题时无法从文件名看出属于哪个账号。

> **本节结论经过修正。** 初稿判断"真实学号命名空间下碰撞概率极低，**无法构造可复现用例**"，因而只作建议。复核后发现碰撞**是确定可复现的**：`"Aa"` 与 `"BB"` 是 `String.hashCode()` 的经典碰撞对（都等于 `2112`），故旧口径下两个不同账号会映射到**同一个缓存文件**。虽然这两个串本身不是学号，但缺陷类（"不同账号共用同一文件"）已可被单测稳定复现，因此从"建议"升级为"**已修复**"。

**修复**（`academic/MessageCenterManager.kt`）：

```kotlin
    internal fun normalizeAccountKey(accountKey: String): String =
        accountKey.ifBlank { "default" }.replace(Regex("[^A-Za-z0-9_.-]"), "_")

    internal fun cacheFileName(accountKey: String): String =
        "message_center_" + normalizeAccountKey(accountKey) + ".json"

    /** 旧口径（`hashCode()`）的文件名，**仅用于读取并迁移历史缓存**。 */
    internal fun legacyCacheFileName(accountKey: String): String =
        "message_center_" + accountKey.hashCode().toString(36) + ".json"
```

`readCache` 增加**一次性迁移**：新文件名不存在时回退读旧文件，读到后改写成新文件名并删掉旧的；`writeCache` 写入新文件后顺手删旧文件；`clearCache` 两个形态都删。迁移失败不影响本次读取 —— 数据落在 `cacheDir`，随时可重新抓取，故迁移无数据丢失风险。

**回归测试**（`MessageCenterCacheCodecTest` 追加 4 项，合计 8 项）：归一化口径一致性、空键回退 `default`、**碰撞对 `"Aa"`/`"BB"` 在旧口径下同名而在新口径下不同名**、旧口径函数为迁移而保留。

### 4.4　`ScheduleSettingsManager` 的账号键未在存储层归一化（**已加固**）

§3.9 的模式排查中，逐个核对了 19 个同时使用两种账号键的文件，发现 `manager/ScheduleSettingsManager.kt` 是**唯一**一个"接收外部账号键、却不自己归一化"的存储层：

```kotlin
    private fun customCoursesKey(accountKey: String): String {
        return "${KEY_CUSTOM_COURSES}_$accountKey"      // ← 直接拼接，依赖调用方传对形态
    }
```

**当前不是可复现缺陷**：`ScheduleRoute`（`routeAccountKey`）与 `WidgetBoardRoute`（`accountKey`）传的都是 `currentAccountStorageKey`，与默认参数 `accountStorageKey()` 一致，所以数据没有被劈开。

**但它正是 P0-1 的成因形态**：一旦有调用方传 `currentAccountKey`（`hnnu::2024001`），就会写到 `custom_courses_hnnu::2024001`，而默认路径读的是 `custom_courses_hnnu__2024001` —— 自定义课程凭空消失，且**没有任何报错**。

**加固后代码**（对现有调用方是空操作，无迁移）

```kotlin
    private fun normalizeAccountKey(accountKey: String): String =
        accountKey.ifBlank { "default" }.replace(Regex("[^A-Za-z0-9_.-]"), "_")

    private fun accountStorageKey(): String =
        normalizeAccountKey(UserManager.getInstance().currentAccountStorageKey.ifBlank { "default" })

    private fun customCoursesKey(accountKey: String): String =
        "${KEY_CUSTOM_COURSES}_${normalizeAccountKey(accountKey)}"
```

> **为什么是空操作**：`currentAccountStorageKey` 的字符集已被 `toStorageKey()` 限定在 `[A-Za-z0-9_.-]` 内（下划线、点、连字符都在允许集合里），再跑一次归一化结果不变。因此**现有用户的键不受影响，无需迁移逻辑** —— 这一点已由新增测试钉住（`SchedulePersistenceTest.customCoursesAreStoredUnderTheSameSlotWhateverKeyShapeCallersUse`：用两种形态的键读写必须命中同一槽位）。
>
> 与 §4.1 / §4.2 / §4.3 不同，本项**已修改代码**：它属于"零风险的潜在缺陷消除"，不像 §4.1 那样需要真机回归。
