## 二、已确认的缺陷

### 🔴 P1-1　同一题在一次会话内会被重复记入数据库　✅ 已修复

**位置**
- `ui/PracticeScreen.kt:461-465`（`onConfirm`）
- `ui/PracticeScreen.kt:466-469`（`onUnjudge`）
- `ui/PracticeScreen.kt:176-181`（`submit` 里的 `judgePending` 补判）

**现象**

```kotlin
onConfirm = {
    val correct = session.judge(current)
    answerVersion++
    record(current, correct)      // ← 每次确认都落库，没有"这题已经记过"的判断
},
onUnjudge = {
    session.unjudge(current)      // ← 只改内存，不撤销已落库的记录
    answerVersion++
},
```

用户点「确认答案」→「再想一下」→ 再确认一次，这道题在 `records` 里就被记了两次；交卷时 `judgePending()` 还会把"已判过但被撤回"的题再记一次。

**影响（都会显示成错误的数据，且不报错）**

1. `records.correct_count` / `wrong_count` 虚高。详情页的正确率是 `accuracyPercent(ov.correct, ov.answered)`（`BankDetailScreen.kt:212`），其中 `correct` 是 `SUM(correct_count)`（**次数**）、`answered` 是 `COUNT(*)`（**题数**）—— 两个口径本来就不同量纲，再叠加重复计数，`correct` 很容易超过 `answered`，被 `coerceIn` 夹成**恒等于 100%**；
2. `wrong_book.streak` 被单次会话刷满 —— **点三次「再想一下」再答对，这道题就被标成「已掌握」**，而用户实际只答对了一次；
3. `due_at` 按被刷高的等级重排 → 间隔复习节奏整个失真。

**建议修法**

最小改动：在 `PracticeScreen` 维护 `recordedKeys: MutableSet<String>`（`bankId::qid`），`record()` 前先判重：

```kotlin
val recorded = remember { mutableSetOf<String>() }
fun record(q: ReviewQuestion, correct: Boolean) {
    if (!recorded.add("${q.bankId}::${q.id}")) return   // 本会话只记一次
    ...
}
```

但这会让"第一次答错、后来想通答对"仍按第一次算。更彻底的做法是**以最后一次判分为准**：给 `records` 增一列 `last_result`（已有）并改成"替换"而不是"累加"，或在会话结束时按最终状态一次性覆盖本轮记录。

> 工作量：去重方案 0.5h（含单测）；"以最后一次为准"方案约半天（涉及 schema 语义）。

### 🟠 P2-2　每次作答都把整轮会话重新序列化成 JSON　✅ 已修复

**位置**：`ui/PracticeScreen.kt:288-291`

```kotlin
LaunchedEffect(answerVersion, session) {
    val encoded = session.exportState()          // 全量编码
    if (encoded.isNotEmpty() || answersSnapshot.isEmpty()) answersSnapshot = encoded
}
```

`answerVersion` 每选一个选项就 +1，于是**每点一次选项都把所有题的作答与判分状态重新拼一遍 JSON**。320 题的题库连答 320 次，就是 320 次 O(n) 编码 ≈ 5 万次字符串拼接，且每次都写入 `rememberSaveable` → 触发 Bundle 更新。

**建议**：改为按 300ms 节流，或只在"一题判分 / 翻页 / 离开页面"时编码。也可以只写增量（当前题）而不是全量。

> 工作量：0.5h。

---

### 🟠 P2-3　`recordAnswers` 是 N+1 写库　✅ 已修复

**位置**：`ReviewDatabase.kt:726-782`

每落一条作答都要先 `stat()`（一次 `SELECT`）再 `insertWithOnConflict`（一次写），一条记录两个往返。交卷补判几十上百题时，单事务里会跑上百次 `SELECT` + 上百次 UPSERT。

**建议**：先一次性 `SELECT bank_id, qid, correct_count, wrong_count FROM records WHERE ...` 预读本轮涉及的题（`IN (...)` 分批），再批量 UPSERT；`wrong_book` 同理。写入吞吐可提升一个量级。

> 工作量：2h（含回归）。

---

### 🟠 P2-4　乱序 / 错题优先抽题把整库题干读进内存　✅ 已修复

**位置**：`ReviewDatabase.kt:610-635`

```kotlin
append("SELECT bank_id, qid, type, stem, options, answer, chapter, explanation, source, tags FROM questions")
...
ReviewMode.RANDOM -> rows.sortedWith(randomOrderComparator())
```

排序只需要 `bankId + qid`，但这里把题干、选项 JSON、解析全文一并读进内存再排序。内置题库最大 320 题尚可接受；用户导入 3,000 题的库时内存峰值会到几十 MB，且排序期间持有一份完整副本。

**建议**：排序阶段只 `SELECT bank_id, qid`（轻量行），算好顺序后再按 id 回读需要的题；或者把排序键固化成列（`sort_key INTEGER`，导入时算一次）。

> 工作量：2h。

---

### 🟡 P2-5　首页概览跑 6 条独立查询　✅ 已修复

**位置**：`ReviewDatabase.kt:980-994` + `ReviewSql.kt:overview`

每次进复习首页执行 6 次 `rawQuery`（questions / records / SUM(correct_count) / wrong_book / favorites / banks）。其中对 `records` 的两条是全表扫描。

**建议**：合并成一条 `SELECT (SELECT COUNT(*) FROM questions ...), (SELECT COALESCE(SUM(correct_count),0) FROM records ...), ...`，一次 cursor 取完六个标量。

> 工作量：1h（`ReviewSql` 需同步改 + 单测）。

---

### 🟡 P2-6　正确率每次重组都全量重算　✅ 已修复

**位置**：`ui/PracticeScreen.kt:323`、`review/PracticeSession.kt:240-243`

```kotlin
"第 ${index + 1} / ${session.total} 题 · 正确率 ${(session.accuracy * 100).toInt()}%"
```

`accuracy` 每次都遍历**全部题目**并对每条已判分的题跑一遍 `judgeAnswer`（`uppercase` + `toSortedSet` + `joinToString`）。320 题时每次翻页/作答都是一次约 320 次的字符串排序。

**建议**：在 `PracticeSession` 里缓存 `correctCount`，在 `judge` / `unjudge` / `restoreState` 时增量维护；或把 `accuracy` 改成 `by lazy` + 版本号失效。

> 工作量：1h（含单测）。

### 🟡 P3-7　`AiConfigStore.isConfigured` 每次都做 Keystore 解密　✅ 已修复

**位置**：`AiConfigStore.kt:116-117` → `load()` → `decrypt()`

- 首页 `AiEntryRow`（`ReviewHomeScreen.kt:344-351`）每次进页面解密一次；
- `PracticeAiController.refreshConfig`（`PracticeAiController.kt:169`）每次 `ON_RESUME` 解密一次。

Keystore 解密单次约几毫秒到几十毫秒，低端机上叠在首帧上可感知。

**建议**：进程内缓存解密结果（配置变更 / `clear` 时失效），`isConfigured` 只读缓存。

> 工作量：0.5h。

### 🟡 P3-8　到期判定有两套实现，靠人肉保持一致　✅ 已收敛

**位置**
- Kotlin：`ReviewScheduling.kt:84` `isDue()`
- SQL：`ReviewDatabase.kt:599-605`（`pickQuestions` 的 `dueOnly`）、`858-897`（`dueWrongQuestions` / `dueWrongCount`）

两边目前口径一致（`due_at = 0` 也算到期），但**改一处忘一处就会漂移**，而且漂移不会报错，只表现为"今日待复习的数字和进去后看到的题数对不上"。另外 SQL 分支默认参数直接取 `System.currentTimeMillis()`，无法注入固定时间做边界测试。

**建议**：把 `now` 显式参数化（已有形参，改调用点即可），并在两个文件顶部互相加"必须与 XX 同步"的注释；理想情况下由 `ReviewScheduling` 生成 SQL 片段，只留一处。

> 工作量：1h。

### 🟢 P3-9　内置题库总数硬编码　✅ 已修复

**位置**：`BundledBanks.kt:117` `TOTAL_QUESTION_COUNT = 1059`

题库 JSON 更新后这个数字不会跟着变，界面上「已内置 N 题」会长期说谎。`SPECS` 里其实已有每库 `expectedCount`。

**建议**：`val TOTAL_QUESTION_COUNT get() = SPECS.sumOf { it.expectedCount }`。

> 工作量：5 分钟。

## 三、架构与可维护性

### 3.1 字符串复合键到处都是　✅ 已实施

`PracticeSession.key()`、`QuestionOrder.randomOrderComparator()`、`RecordedKeys` 判重……都在拼 `"$bankId::$qid"`。每次都产生临时字符串，且拼法一旦不一致（少一个 `::`、中间多空格）就会静默失配。

**建议**：给 `ReviewQuestion` 加

```kotlin
val compositeKey: String by lazy { "$bankId::$id" }
```

全模块统一用它。

> 工作量：1h（机械替换）。

### 3.2 `ReviewDatabase.kt` 1,055 行，承担了 6 类职责　✅ 已拆分

建表/迁移、题库 CRUD、抽题、作答落库、错题本、收藏、概览统计全在一个类里。`ReviewSql` 已经抽走了一部分拼装逻辑，但 CRUD 仍然混在一起。

**建议**：按职责拆成 3-4 个 `*Store`（`BankStore` / `QuestionStore` / `RecordStore` / `WrongBookStore`），共用一个 `SQLiteOpenHelper`。不改 schema、不改语义，纯文件切分。

> 工作量：半天，收益是可读性与后续加功能的摩擦。

### 3.3 `PracticeScreen.kt` 556 行里的界面状态偏多　✅ 已收敛

`index / answersSnapshot / restored / showAi / favorite / showAnswerSheet / autoNext / autoAdvanceTick / answerVersion / summary / recordFailureShown / warnedFive / warnedOne` —— 13 个 `remember`。

其中 `answerVersion` 与 `answersSnapshot` 是"绕过 `PracticeSession` 不是 Compose 状态"的补丁。更干净的做法是让 `PracticeSession` 的作答表本身变成 `mutableStateMapOf`，`answerVersion` 整个消失。

> 工作量：半天，风险中等（要重跑全部练习页交互）。
